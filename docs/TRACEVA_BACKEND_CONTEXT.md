# TraceVA — Backend Implementation Context and Coding-Agent Brief

**Status:** Implementation plan, not completed code. **Date:** November 2026. **Priority:** Build a small, correct end-to-end vertical slice before broadening features.

## 0. How the coding agent should use this file

You are implementing the backend of **TraceVA: Explainable Agentic Visual Analytics Through Interactive Analytical Provenance**, an individual graduate visual analytics project. Treat this file as the project's design brief. Before coding, inspect the existing repository, summarize what exists, identify conflicts with this brief, and propose the smallest next increment. Do not overwrite existing work without asking. Prefer clear, testable Python code and incremental commits. If a design decision is unspecified, document the assumption instead of silently expanding scope.

**Core research question:** How can interactive analytical provenance help users inspect, challenge, and refine conclusions generated by an LLM-based data-analysis agent?

**Non-negotiable research distinction:** The system records *actual backend-executed tool calls and their results*, not hidden LLM reasoning. LLM-generated claims and suggested evidence relationships are not automatically verified truths. A revision is not automatically an improvement.

## 1. Product goal and end-to-end demonstration

A user asks a natural-language question about a structured tabular dataset. A tool-calling LLM chooses a limited set of analytical operations. The FastAPI backend validates and executes them deterministically, records the data inputs, parameters, outputs, and timing, and returns compact results to the model. The model creates a natural-language claim with references to real evidence IDs. The frontend can show a chart, the claim's evidence and assumptions, and the temporal history of the analysis. A user can challenge a claim; this creates an immutable child analysis run, records the triggering chat message, executes alternative analysis, and produces a revised claim linked to the original. Both branches remain inspectable and comparable.

**Minimum demo:** `question → executed operation → evidence → grounded claim → user challenge → child run → revised evidence/claim → branch comparison`, with chat events linked to graph nodes.

## 2. Scope and constraints

- **Primary dataset:** UCI Adult Income, with a pinned, locally stored source file, documented column names, missing-value handling, and source hash. Other datasets are registered, not arbitrarily fetched by the model.
- **Secondary evaluation:** controlled synthetic datasets (outliers, aggregation/subgroups, skew, filtering) and a small, *compatible* subset of a published agent data-analysis benchmark (e.g. InfiAgent-DABench). Do not claim direct comparability to published scores if tasks are adapted.
- **MVP tools:** inspect schema, create filtered view, group/aggregate, descriptive stats, correlation (Pearson/Spearman), simple regression, and validated chart specification. Start with 2–3 tools, then expand.
- **No arbitrary LLM-generated Python, SQL, shell commands, or unrestricted file access.** Never let a model write directly to the database.
- **No graph database, multi-agent orchestration, user authentication, cloud deployment, or large user study in MVP.** Local-first, single-user development is acceptable.
- **Do not treat correlation as causation or a change in correlation method as proof of outlier effects.** Surface limitations and assumptions.
- **Evaluation:** correctness, error recovery, regressions after challenge, provenance integrity, temporal consistency, and latency. No claim of improved human performance without a user study.

## 3. Hardware and model strategy

- Available laptops: Intel Iris Xe (integrated graphics) and NVIDIA RTX 4070 Laptop GPU. NVIDIA lists the RTX 4070 Laptop GPU with **8 GB GDDR6**; verify actual device VRAM with `nvidia-smi`. Model context length, quantization, and concurrent processes affect fit.
- **Local development default:** Ollama on Intel Iris Xe laptop. Test actual tool-call reliability, latency, and VRAM; don't assume quality from model family alone. Prefer moderate context windows (e.g. 4k–8k initially) and concise tool outputs. Smaller alternative if needed. CPU-only Iris Xe use is possible but likely slow for interactive reasoning.
- **Hosted reference model:** configurable provider/model through environment variables. Never hardcode API credentials. Do not require paid inference for unit tests.
- **Adapter boundary:** use an `LLMClient` protocol and provider-specific implementations. Initial implementation may use the Python OpenAI SDK against Ollama's OpenAI-compatible `/v1/chat/completions` and a hosted provider. Compatibility is a subset, not a promise of identical semantics. Do not rely on provider-managed conversation state or provider-specific forced tool choice.
- Keep provider, model ID, quantization/tag, prompt version, generation parameters, runtime duration, token usage (when available), and relevant error details in run metadata.
- Use temperature near zero for benchmark repeatability, but still run repeated trials. Log seed if supported; do not promise deterministic inference across hardware/providers.
- Agent quality must be evaluated for valid tool selection, argument accuracy, interpretation, challenge handling, and evidence grounding. Model selection should not deliberately favor a weak model to inflate correction rates.

## 6. Data model and invariants

Use stable opaque IDs (UUID/ULID), UTC timestamps, foreign keys, and explicit schema versions. SQLite foreign-key enforcement must be enabled. Prefer append-only provenance records and immutable dataset views. A run's `status` may transition through a controlled state machine, but completed historical results must not be silently edited.

### Core records

| Record | Essential fields | Meaning |
|---|---|---|
| `DatasetSource` | id, name, file_path, sha256, schema_json, row_count, created_at | Registered immutable input file/version |
| `DatasetView` | id, source_id, parent_view_id?, canonical_filters_json, columns_json, row_count, created_at | Reproducible selection/projection; deterministic canonical definition |
| `Conversation` | id, created_at | Group of user/assistant exchanges |
| `ChatMessage` | id, conversation_id, role, content, created_at, run_id?, sequence_no | Chronological dialogue and its run link |
| `AnalysisRun` | id, conversation_id, question_message_id, parent_run_id?, status, provider/model/config snapshot, created_at, completed_at | One initial investigation or challenge branch |
| `Operation` | id, run_id, triggering_message_id?, tool_name, args_json, input_view_ids, status, started_at, completed_at, error_json? | **Actual** validated backend tool invocation |
| `Evidence` | id, operation_id, result_json, artifact_refs_json?, created_at | Immutable computed result; numerical values and metadata |
| `Claim` | id, run_id, text, status, created_at | Model-authored interpretation; link to evidence separately |
| `Assumption` | id, text, source (`agent_stated` or `method_template`), status, created_at | Stated assumption or backend-added methodological caveat |
| `Revision` | id, parent_run_id, child_run_id, challenge_message_id, target_claim_id?, changes_json, created_at | Why and how the branch diverged |
| `ProvenanceEdge` | id, from_id, to_id, type, origin, created_at | Typed graph relationship |
| `TimelineEvent` | id, conversation_id, run_id?, message_id?, event_type, entity_id?, sequence_no, occurred_at | UI synchronization and replayable event order |

Possible edges: `CONSUMES` (operation→view), `PRODUCES` (operation→evidence/view), `SUPPORTS`/`CONTRADICTS` (evidence→claim, **interpretive**), `QUALIFIES` (assumption→claim/operation), `REVISES` (new claim→old claim), `BRANCHES_FROM` (child run→parent run). Add `origin=backend_verified|agent_proposed|method_template` to distinguish epistemic status. Enforce valid endpoint types in application logic; a generic ID pair alone is insufficient.

**Important invariants:**
1. An `Evidence` record must refer to an executed `Operation`, never an LLM invention.
2. A `Claim` can cite only evidence IDs visible in its run/allowed ancestors, checked server-side; evidence links are not automatically proof of claim correctness.
3. Revisions create new run IDs and new records; they do not mutate old claims or operations. Old run states remain queryable.
4. A timeline event references the chat/run/entity that caused it; timestamps and sequence numbers are both stored. Temporal adjacency **does not imply** analytical dependency.
5. A failed or invalid tool call is logged as an attempted operation with error metadata, but must not produce successful evidence.
6. Dataset views must preserve filters, column selections, null handling, and source hash so operations can be replayed.
7. Methodological caveats should not be represented as tested assumptions unless actually checked.
8. Avoid logging hidden model chain-of-thought; store tool calls, model-visible messages, public explanations, and explicit outputs only.

### Event types (starting vocabulary)

`USER_MESSAGE`, `RUN_STARTED`, `TOOL_REQUESTED`, `TOOL_SUCCEEDED`, `TOOL_FAILED`, `EVIDENCE_CREATED`, `CLAIM_CREATED`, `ASSUMPTION_RECORDED`, `CHALLENGE_SUBMITTED`, `BRANCH_CREATED`, `RUN_COMPLETED`, `RUN_FAILED`.

The frontend can query timeline events ordered by `sequence_no` and request the graph snapshot at a selected event, using `sequence_no <= selected_event.sequence_no` (subject to run/branch visibility). Preserve full immutable history.

## 7. Analytical tool contracts

**Tools must be ordinary Python functions with typed Pydantic input/output contracts.** Expose a small safe subset to the LLM via JSON Schema. The same functions should be callable directly from tests and benchmark scripts without an LLM.

Start with:

1. `inspect_dataset(source_id)`: schema, types, row count, missingness summary, compact categorical examples; no raw full-table dump.
2. `create_view(source_or_view_id, filters, columns, null_policy)`: validated typed filters with allowlisted operators, deterministic view definition and row count.
3. `summarize(view_id, columns, group_by?, metrics)`: counts, mean/median/std/min/max, proportions with explicit denominator and missingness.
4. `correlate(view_id, x, y, method)`: Pearson/Spearman, `n`, missing-value policy, coefficient, optional p-value and caveats. Only numeric columns; reject invalid/constant inputs gracefully.
5. `fit_regression(view_id, target, predictors, model_type)`: only explicitly supported model types (e.g. OLS for numeric outcomes, logistic for binary outcomes), sample size, coefficient metadata, warnings. Implement after core tools are stable.
6. `build_chart_spec(view_id, chart_type, x, y?, group_by?, evidence_ids?)`: backend-validated Plotly-friendly declarative spec/data; no arbitrary executable JS or raw HTML.

Use controlled filter expression AST rather than freeform query strings. Validate field existence, dtype, allowed aggregation, row limits, and incompatible argument combinations. Make default missing-value behavior explicit. Return compact structured results with stable IDs and machine-readable error codes. Never return tens of thousands of records to the model.

Example request/response (illustrative, **not real Adult Income statistics**):

```json
{
  "tool": "correlate",
  "arguments": {"view_id": "view_123", "x": "age", "y": "hours_per_week", "method": "spearman"}
}
```

```json
{
  "operation_id": "op_456",
  "evidence_id": "ev_789",
  "result": {"method": "spearman", "coefficient": 0.12, "n": 1000, "missing_policy": "pairwise_drop"},
  "caveats": ["Association does not establish causation"]
}
```

## 8. Agent orchestration contract

1. Accept a persisted user message and create a new `AnalysisRun` (or child run for a challenge).
2. Build compact model context: dataset schema, user question, relevant prior claims/evidence, tool descriptions, and explicit constraints. Do not send the entire dataframe.
3. Call the model; parse tool calls defensively. Validate all arguments server-side, even when a provider advertises strict structured outputs.
4. Execute via tool registry. Log attempted operation and result/exception in database transaction(s); create immutable evidence only after successful execution.
5. Send the compact tool result and real evidence ID back to the model. Repeat up to a configurable tool-step and token/time budget. Support multiple tool calls if provider returns them, with deterministic execution order initially.
6. Obtain a final structured response: explanation, list of claims with **existing evidence IDs**, explicit caveats, optional chart IDs. Validate and persist claim/evidence links; reject or request repair of nonexistent references.
7. Emit `RUN_COMPLETED` or `RUN_FAILED`; return run ID, messages, claims, evidence refs, chart specs, and event cursor.
8. Handle provider timeouts, malformed calls, model refusal, unsupported questions, infinite loops, and budget exhaustion with typed errors and partial provenance, not silent failure.

**Prompts:** ask for accurate, concise interpretation, no invented numbers/evidence, no unsupported causality, and explicit uncertainty. The model may propose assumptions, but the backend separately adds method-derived caveats. The model should not be asked to produce hidden reasoning traces.

**Challenge flow:** persist user challenge and target claim; create child run with parent reference; include original question, selected prior evidence and challenge; execute new tools; create new claims and explicit `REVISES` links where justified. A challenge can confirm the original claim, weaken it, contradict it, or remain inconclusive. Never force an improvement narrative.

## 9. API sketch (proposed, versioned)

- `GET /api/v1/health` — service status and optionally model availability (no secrets).
- `GET /api/v1/datasets` — registered datasets and schema summaries.
- `POST /api/v1/conversations` — start conversation.
- `GET /api/v1/conversations/{id}/messages` — ordered messages.
- `POST /api/v1/conversations/{id}/messages` — submit question; returns run/response (synchronous MVP).
- `POST /api/v1/runs/{id}/challenges` — target claim ID + challenge text; creates child run.
- `GET /api/v1/runs/{id}` — run status, claims, evidence, chart refs.
- `GET /api/v1/runs/{id}/graph` — typed nodes and edges, provenance origin and timestamps.
- `GET /api/v1/conversations/{id}/timeline` — ordered events with linked messages and nodes.
- `GET /api/v1/runs/{id}/compare/{other_run_id}` — structured differences between two runs/branches.

Use consistent errors (`code`, `message`, `details`, `request_id`), pagination for timeline/messages, and explicit data types. For long-running analysis, transition to `202 Accepted` + polling or SSE; don't prematurely implement both.

## 10. Research evaluation requirements

### A. Known-answer benchmark
- ~12–15 curated Adult Income tasks with independently computed reference answers.
- Score numerical correctness (with defined tolerances), tool choice, filter/grouping correctness, and claim validity. Keep answer rubrics outside model context.

### B. Synthetic pitfalls / assumption challenges
- ~4–6 scenarios: aggregate vs subgroup relationship, outliers, skewed mean vs median, filtering/missingness, and correlation-vs-causation interpretation.
- Predefine challenges **without revealing ground truth**; include initially correct analyses to measure regressions.
- Record initial correctness, revised correctness, recovery rate conditional on initial failure, and regression rate conditional on initial success. Also score whether revision addresses the challenge.

### C. External benchmark
- Select ~5–8 compatible tasks from InfiAgent-DABench or another documented agent reliability benchmark; document inclusion/exclusion criteria and adaptations. Benchmark availability/licensing must be verified before ingestion.
- Report as a curated subset, not an official full-benchmark score. Keep tasks, reference answers, and scoring separated from model prompt.

### D. Provenance/temporal integrity
- Automated tests: all evidence links resolve; operation replay matches outputs; old branches unchanged; invalid IDs rejected; chat-to-run links correct; event order stable; historical snapshots reconstructible; timeline adjacency not conflated with dependency edges.

### E. Model comparison (development decision, not necessarily research contribution)
- Compare local model and hosted baseline on same prompts/tools/datasets, with multiple trials. Metrics: tool validity, end-to-end accuracy, interpretation, challenge success, latency, estimated token usage and cost.
- Record provider/model/config and failures; no cherry-picking successful runs.

## 11. Testing and safety

- Unit tests for statistics and typed filters (including empty views, missing values, nonnumeric columns, zero variance, group denominator correctness).
- Integration tests for `question → operation → evidence → claim` using a **fake deterministic LLM client**; tests must not require Ollama or paid API access.
- Integration tests for challenge branching and historical timeline replay.
- Validate source file hashes and dataset/view IDs; reject path traversal, unknown columns, oversized filters, unsupported chart types, arbitrary SQL/code, and oversized model output.
- Set tool-step, runtime, output-row, context, and retry limits. Retry transient model failures with bounded backoff; do not blindly retry operations that could duplicate records.
- Store secrets in environment variables, not DB/logs/repo. Log prompt/tool summaries with privacy awareness; avoid dumping full data into logs.
- SQLite is sufficient for local single-user MVP. Manage transactions carefully; do not hold a DB transaction open during a slow model inference call. For concurrent runs, handle SQLite write contention and idempotency.

## 12. Delivery milestones / acceptance criteria

**Milestone 0 — Repository bootstrap**
- FastAPI app starts, `/health` works, config and SQLite migrations work, pytest passes, `.env.example` documented.

**Milestone 1 — Deterministic analysis engine**
- Adult dataset registered with source hash; inspect, filtered view, and grouped summary tools return tested structured results. No LLM yet.

**Milestone 2 — Agent vertical slice**
- Ollama model selects and executes at least one real tool; a grounded claim references a real evidence ID. Same path works with fake LLM in CI.

**Milestone 3 — Provenance + temporal chat**
- Tool execution, claims, assumptions, chat messages, and timeline events persisted; API returns typed graph and chronological event list. Chat selection can resolve related node IDs.

**Milestone 4 — Immutable challenge branch**
- Challenge creates child run; both original and revised evidence/claims persist; compare API identifies changed methods/results; original history unchanged.

**Milestone 5 — Evaluation + hardening**
- Benchmark runner exports machine-readable results (JSON/CSV), tests for provenance integrity and replay, reproducible model configuration, clear failure reports.

**Definition of done for MVP:** A new developer can follow README setup, load the dataset, run tests without model access, start Ollama, ask one analytical question through the API, inspect evidence/provenance, challenge the claim, and retrieve a comparison of both branches.
